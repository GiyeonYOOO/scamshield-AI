# F3020 실행 로그 이상 징후와 원인 진단

2026-11-18에 SSAFY 3회차 프로젝트 명세서의 F3020 범위를 검증했습니다. [요구사항 PDF](<../../AI코어프로젝트_3회차_요구사항정의서.pdf>)

## 구조와 F3021 연동

1. `LoggingAgent.record()`는 SQLite에 원본 이벤트를 저장합니다.
2. FastAPI의 별도 구독자는 `run.finished` 뒤 해당 실행의 이벤트를 읽고 `evaluate_events()`로 판정합니다. Python에서는 `LoggingAgent.evaluate(session_id, run_id, decider)`로 다시 판정할 수 있습니다.
3. 규칙 판정은 `execution_evaluations`에 저장합니다. 종료된 실행에서 경고가 있고 LLM이 설정됐을 때만 `execution_diagnoses`에 호출 권한을 원자적으로 기록한 뒤 진단합니다. 실패하면 오류 코드를 별도 저장합니다.
4. F3021의 요청 중 검증은 기존 경로를 사용합니다. Planner는 `LoggingAgent.verify()`가 반환한 규칙 판정으로 작업 결과를 제외하거나 재계획합니다. F3020은 동일 입력 비교와 고정 인자 비교 규칙을 공유하며, F3021의 `audit.checked` 이상 코드와 실제 이벤트를 함께 기록합니다. 종료 후 모델 진단은 재계획의 입력으로 사용하지 않습니다.

## 판정 규칙

| 이상 징후 | 기록 근거 |
|---|---|
| 동일 입력 반복 | Tool 이름, 실행 안에서만 같은 URL을 연결할 수 있는 HMAC 참조, 조회 일수가 모두 같은 두 호출. 허용된 Worker 재시도에서 조회 일수가 달라지면 이 규칙에 해당하지 않습니다. 재시도 상한과 변경 허용 여부는 F3021 감사 결과로 확인합니다. |
| 과도한 재계획 | `run.started.max_replans`와 실제 수행된 `replan.decided` 수 또는 기록된 카운터를 비교합니다. 재계획 검토만 하고 종료한 이벤트는 세지 않습니다. |
| 계획 외 Tool과 고정 인자 변경 | 해당 계획 차수의 `planner.task`, `worker.attempt`, 실제 `tool.requested`를 대조합니다. F3021의 이미 확인된 이상 코드도 활용합니다. |
| 계획과 결과 불일치 | F3021의 호출·결과 대조에서 얻은 순서·호출 누락 또는 추가·허용되지 않은 재시도 코드를 사용합니다. 원본 로그가 부족하면 불일치를 추정하지 않습니다. |

경고에는 코드, 발생 위치(계획 차수와 이벤트 순번), 규칙이 설명하는 이유, 실제 이벤트 ID 목록을 포함합니다. ID는 기존 원본 로그의 키와 같은 `실행 ID:순번` 형식입니다. 같은 코드와 계획 차수에서 중복 발견된 근거는 한 경고에 합칩니다.

`normal`은 필요한 이벤트가 갖춰지고 위반이 없는 경우, `warning`은 근거가 있는 위반이 있는 경우, `inconclusive`는 필요한 기록이 부족해 판단을 마칠 수 없는 경우입니다. 시작·종료나 작업 대조 이벤트가 빠진 경우, 실행에 Tool 호출이 있지만 단일 Agent 로그라 작업 목록이 없는 경우, 이전 포맷에 필요한 필드가 없는 경우가 판정 불가에 해당할 수 있습니다. 일부 기록이 빠져도 직접 확인된 위반은 경고로 보존하고 `complete=false`를 표시합니다.

## 모델 진단과 개인정보

모델에는 경고 코드와 이벤트 순번만 전달합니다. 모델이 Planner·Worker·Tool 중 관련성이 높은 구성 요소와 실제 경고 코드를 선택하면, 검증된 근거와 수정 제안을 한국어 3문장으로 구성합니다. 진단은 모델이 제시한 원인 가능성이며 확정 원인을 뜻하지 않습니다. 모델에 사용자 메시지, URL, 공급자 응답, API 키와 HMAC 키를 제공하지 않습니다. URL 비교용 HMAC 키는 실행마다 새로 생성해 메모리에만 둡니다.

판정과 진단은 세션 참조 및 실행 ID로 분리 저장합니다. 같은 실행을 반복 평가하거나 동시에 평가해도 동일 경고가 누적되거나 진단이 다시 호출되지 않습니다. 원본 로그는 기존 수정 차단 트리거를 유지하고, 로그 삭제 시 해당 판정과 진단도 삭제합니다.

조회는 `GET /api/logs/{run_id}/evaluation` 또는 `ExecutionLogs.get_evaluation(session_id, run_id)`를 사용합니다. 결과에는 상태, 경고와 근거, 판정 불가 사유, 별도 진단이 포함됩니다. 다른 세션의 실행에는 접근할 수 없습니다. 이전 로그의 조회는 규칙 평가만 수행합니다.

## 실제·모의 검증

| 구분 | 결과 |
|---|---|
| 실제 정상 FastAPI·GMS·Google Safe Browsing | 공개 URL에서 HTTP 200과 Google `NO_MATCH`를 반환했습니다. 규칙 판정 `normal`, 경고 0건, F3020 진단 호출 0회였습니다. |
| 실제 GMS 진단 + 통제된 SQLite 이벤트 | 동일 Tool·입력의 중복 호출 이벤트를 주입했습니다. 실제 외부 Tool 중복 호출 없이 `DUPLICATE_CALL` 경고 1건과 GMS 진단 `completed`를 저장했습니다. GMS는 Planner를 관련 구성 요소로 선택했습니다. 재평가 결과가 동일했고 전체 진단 호출은 1회였습니다. |
| 모의·로컬 회귀 | 기존 80개와 신규 8개, 총 88개 통과. 정상 재시도, 중복·상한·고정 인자·계획 외 호출 감지, 판정 불가, 진단 오류 후 결과 유지, 동시 판정 중복 방지, 세션 조회 분리와 로그 삭제를 확인했습니다. |

## 제한사항

F3020 진단은 이상 실행의 종료 뒤 동기로 호출됩니다. 정상 경로에서는 이 진단 호출이 없지만, 경고가 있는 요청은 설정된 모델 응답 시간만큼 늦어질 수 있습니다. 진단 도중 프로세스가 종료되면 그 실행의 진단 행이 `pending`으로 남을 수 있으며 자동 재호출은 없습니다. 이전 단일 Agent 로그는 새 고정 인자 비교나 계획·결과 대조를 완전히 재현하기 어렵습니다. F3021의 불완전 보고서 검토 호출은 별도 경로입니다.
